# StackHarbor 协议 v2

配置版本与 CLI JSON schema 版本分别管理。v1 文件和原 `project/service` ID 继续支持；v2 使用下面的显式节点，不自动猜拆旧启动脚本。

| 节点 | ID | 依赖条件 | 成功含义 |
|---|---|---|---|
| resource | `resource/database` | available | 指定 Compose 服务满足 running / healthy |
| task | `backend/task/migrate` | succeeded | 检查、执行及必要复验成功结束 |
| service | `backend/service/api` | started / ready | 进程存活 / 所配置探针成功 |

启动、停止、重启和导航使用同一份 DAG。启动取传递前置闭包；停止逆序处理运行中的后继；重启恢复原运行的后继集合。无关分支继续运行。总览先显示基础设施，再按依赖显示任务、应用和前端；跨工程交叉依赖按阶段分组。

## 工程注册

```yaml
version: 2
project: {id: backend, name: Backend}
context:
  cwd: .
  env_files: [../.env]
  env: {PAGESMITH_CREATE_TABLES: "false"}
tasks:
  preflight:
    effect: read-only
    policy: always
    timeout_seconds: 30
    run: {command: [python, scripts/preflight.py]}
  migrate:
    effect: schema-write
    policy: when-needed
    inputs: [alembic.ini, migrations, scripts/migration_status.py]
    requires:
      - {node: backend/task/preflight, condition: succeeded}
      - {node: resource/database, condition: available}
    lock:
      scope: database
      target: {env: PAGESMITH_DATABASE_URL}
      schema: public
    check:
      command: [python, scripts/migration_status.py]
      satisfied_exit: 0
      needed_exit: 10
      drift_exit: 20
      required_scope: [migration_chain, pending_create_table_conflicts]
    run: {command: [python, -m, alembic, upgrade, head]}
    verify:
      command: [python, scripts/migration_status.py]
      success_exit: 0
      required_scope: [migration_chain, target_table_column_presence]
    timeout_seconds: 180
services:
  api:
    run: {command: [python, server.py]}
    requires: [{node: backend/task/migrate, condition: succeeded}]
    ports: [{name: http, port: 5600}]
    ready: {tcp: "127.0.0.1:5600", timeout_seconds: 60}
    stop: {signal: INT, timeout_seconds: 15}
```

环境顺序：进程环境 → 有序 env_files → context.env → 节点 env。各阶段使用同一快照。env_files 是简单赋值文件，支持注释、export 和单/双引号包裹的单行值，不进行 shell 展开或转义解释；缺失、超出根边界、插值或格式错误会拒绝。cwd/env_files 相对注册文件；task.inputs 相对实际 cwd。输入目录最多 1000 文件、单文件 4 MiB，忽略 `.git` / `__pycache__`，不接受符号链接。注册、环境文件、Compose 及声明 inputs 改变后需重开会话。需要监测迁移脚本变化时必须声明 inputs。

所有命令是 argv。unknown 字段、重复 ID/端口、缺失依赖、环和条件/类别不匹配均拒绝。任务 timeout 1–600 秒，默认 120；依赖等待 600 秒、锁等待 60 秒。等待依赖或数据库锁不占执行槽，执行并发最多 4。

effect 支持 read-only、schema-write、environment-write、data-write。always 仅允许 read-only；when-needed 强制 check/verify；manual 不会被自动依赖或默认全部启动包含。schema-write 还必须配置显式 PostgreSQL 目标锁。read-only 是脚本契约，不是权限沙箱。

## 检查、迁移和诊断

check 的 stdout 必须是单个有界 JSON 对象，人工日志写 stderr。格式：

```json
{"schema_version":1,"status":"drift","code":"migration.schema_conflict","message":"表存在但创建迁移未登记","checked_scope":["migration_chain","pending_create_table_conflicts"],"target_revisions":["目标版本"],"remediation":"核对结构及数据迁移效果，人工协调"}
```

退出 0 / 10 / 20 必须对应 satisfied / needed / drift。无效 JSON、未知码、缺失 required_scope、超时均不放行。needed 才执行 run，run 退出 0 后仍须 verify 为 satisfied。check/verify 的 target_revisions 必须相同。成功检查但无需执行显示“已满足，未执行”；下一次计划重新检查。

PostgreSQL URL 支持 postgres、postgresql、postgresql+psycopg2。锁由目标数据库上的固定 advisory key 提供，同库不同账号、地址别名和 workspace 互斥；database scope 不按 schema 分锁。持锁连接贯穿取锁后的 check→run→verify，连接失效取消执行。schema 字段仅描述检查目标，不改变数据库级锁范围；检查脚本负责按实际连接设置验证 schema。shared_id 目前拒绝。

需要迁移时如受管消费者仍运行或数据库有其他客户端连接，任务阻塞并报告维护范围，不自动在线改表。需先显式停止消费者再重试。其他客户端观测要求 pg_read_all_stats 或等价可见性，权限不足拒绝写迁移。数据库客户端观测是一个保守快照，不能阻止不遵守协议的客户端随后连接；第一版不支持在线迁移或自动维护恢复事务。漂移不自动 stamp/drop。写任务中断记 unknown，重新检查后才能恢复。

PageSmith 适配器仅验证版本链、待建表名称冲突、到目标时 ORM 表/字段存在性；它不证明全部类型、索引、触发器和历史数据迁移已经正确。这些项目在人工协调前单独审计。`conflicting_tables` 保留完整列表，界面显示摘要及处理建议。

## 显式资源和观察服务

workspace：

```yaml
version: 2
root: .
discover: false
registrations: [.stackharbor/backend.yaml]
resources:
  database:
    name: PostgreSQL
    adapter: compose
    file: docker-compose.yml
    project: pagesmith
    service: db
    available: healthy
    control: managed
    lifetime: persistent
```

file/project/service 是精确资源身份；file 必须在根内。healthy 要求 Compose healthcheck。control 为 managed / observe；lifetime 为 persistent / session。停止单工程或全部应用不停止持久容器，q 保留 persistent / observe 资源；容器停止/重启是明确动作并处理受管后继。`d` 在 v2 中只显示显式注册资源，多个 Compose project 通过 node ID 分别控制。持续观测健康和容器 ID；实例改变要求重新检查依赖。

当前支持一个资源对应单 Compose 文件、service_started / service_healthy 边。Compose 依赖必须也显式注册；一次性完成依赖、optional/restart 扩展、include/profiles/extends、多文件合成暂不支持，验证时拒绝，不能静默降级。不会 build、删除卷或隐式启动未声明的依赖。

观察服务 `control: observe` 不得有 run/stop；要求 ports、ready、`identity: {command: [绝对可执行文件, 参数前缀]}`。身份核对监听 PID/创建时间、cwd 与 argv 前缀，失败不得满足依赖；只读观察不获得停止权限。进程更换需要重新核验。受管服务无探针显示 started，v1 依赖语义保持兼容。

## CLI 与记录

```sh
stackharbor validate --workspace workspace.yaml --json
stackharbor plan start --target backend/service/api --workspace workspace.yaml
stackharbor doctor --target backend/task/migrate --workspace workspace.yaml
stackharbor task run backend/task/migrate --workspace workspace.yaml
stackharbor history --root /path/to/project
```

plan 只读且不执行脚本，导出配置摘要、目标、拓扑层、边和动作；迁移状态和停止/重启的实际运行集合注明待执行时核验。它不是预先授权在线迁移的凭证。doctor 显式执行只读检查阶段；非 0 检查返回运行失败。task run 是显式执行，会处理任务资源前置项。

事件和任务阶段日志写入缓存中 root 对应的 `.lock.events.jsonl`，带 operation/attempt ID，0600、2 MiB 轮转、保留一份 previous。history 只读，允许读取当前会话；忽略未写完的末行，其他损坏报错。常见 secret/password/token 环境值与 URL 用户信息脱敏；自定义未知秘密仍应由适配器清洗。记录可审阅，不自动恢复旧 PID 或盲信旧任务结果。

兼容：v1 workspace 可显式导入 v1/v2 注册文件，保留已有 v1 节点 ID；workspace 自身声明 resources 时必须为 version 2。纯 v1 discover/validate 仍是 JSON schema 1；含 v2 注册的 workspace 输出 schema 2 的节点投影，均不输出环境值。
