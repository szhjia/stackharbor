# StackHarbor protocol v2

Configuration versions and CLI JSON schema versions are managed separately. v1 files and the original `project/service` IDs remain supported. v2 uses the explicit nodes below and does not automatically infer how to split existing startup scripts.

| Node | ID | Dependency condition | Meaning of success |
|---|---|---|---|
| resource | `resource/database` | available | The specified Compose service satisfies running / healthy |
| task | `backend/task/migrate` | succeeded | Checks, execution, and any required verification finish successfully |
| service | `backend/service/api` | started / ready | The process is alive / the configured probe succeeds |

Start, stop, restart, and navigation use the same DAG. Start includes all transitive prerequisites; stop handles running downstream nodes in reverse order; restart restores the previously running downstream set. Unrelated branches keep running. The overview shows infrastructure first, followed by tasks, applications, and frontends in dependency order; dependencies across projects are grouped by stage.

## Project registration

```yaml
version: 2
project: {id: backend, name: Backend}
context:
  cwd: .
  env_files: [../.env]
  env: {PAGESMITH_CREATE_TABLES: "false"}
tasks:
  preflight:
    effect: read-only
    policy: always
    timeout_seconds: 30
    run: {command: [python, scripts/preflight.py]}
  migrate:
    effect: schema-write
    policy: when-needed
    inputs: [alembic.ini, migrations, scripts/migration_status.py]
    requires:
      - {node: backend/task/preflight, condition: succeeded}
      - {node: resource/database, condition: available}
    lock:
      scope: database
      target: {env: PAGESMITH_DATABASE_URL}
      schema: public
    check:
      command: [python, scripts/migration_status.py]
      satisfied_exit: 0
      needed_exit: 10
      drift_exit: 20
      required_scope: [migration_chain, pending_create_table_conflicts]
    run: {command: [python, -m, alembic, upgrade, head]}
    verify:
      command: [python, scripts/migration_status.py]
      success_exit: 0
      required_scope: [migration_chain, target_table_column_presence]
    timeout_seconds: 180
services:
  api:
    run: {command: [python, server.py]}
    requires: [{node: backend/task/migrate, condition: succeeded}]
    ports: [{name: http, port: 5600}]
    ready: {tcp: "127.0.0.1:5600", timeout_seconds: 60}
    stop: {signal: INT, timeout_seconds: 15}
```

Environment precedence: process environment → ordered env_files → context.env → node env. Each stage uses the same snapshot. env_files are simple assignment files supporting comments, export, and single-line values enclosed in single or double quotes; no shell expansion or escape interpretation is performed. Missing files, paths outside the root boundary, interpolation, or invalid syntax are rejected. cwd/env_files are relative to the registration file; task.inputs are relative to the actual cwd. Input directories are limited to 1000 files, each at most 4 MiB; `.git` / `__pycache__` are ignored and symlinks are rejected. Reopen the session after registrations, environment files, Compose files, or declared inputs change. Declare inputs whenever changes to migration scripts need to be detected.

All commands are argv arrays. Unknown fields, duplicate IDs/ports, missing dependencies, cycles, and mismatches between conditions and node kinds are rejected. Task timeouts are 1–600 seconds, defaulting to 120; dependency waits are 600 seconds and lock waits are 60 seconds. Waiting for dependencies or a database lock does not occupy an execution slot; at most 4 tasks execute concurrently.

effect supports read-only, schema-write, environment-write, and data-write. always permits only read-only; when-needed requires check/verify; manual is excluded from automatic dependency execution and the default start-all action. schema-write also requires an explicit PostgreSQL target lock. read-only is a script contract, not a permission sandbox.

## Checks, migrations, and diagnostics

check stdout must contain a single bounded JSON object; write human-readable logs to stderr. Format:

```json
{"schema_version":1,"status":"drift","code":"migration.schema_conflict","message":"The table exists but its creation migration is not recorded","checked_scope":["migration_chain","pending_create_table_conflicts"],"target_revisions":["target revision"],"remediation":"Review the schema and data migration results, then reconcile manually"}
```

Exit codes 0 / 10 / 20 must correspond to satisfied / needed / drift. Invalid JSON, unknown codes, missing required_scope coverage, and timeouts prevent execution from proceeding. run executes only for needed; after run exits with 0, verify must still report satisfied. check/verify must report the same target_revisions. A successful check that needs no execution is displayed as “Satisfied, not executed”; the next plan checks again.

PostgreSQL URLs support postgres, postgresql, and postgresql+psycopg2. A fixed advisory key in the target database provides the lock, enforcing mutual exclusion across different accounts, address aliases, and workspaces using the same database; database scope does not partition locks by schema. The lock-holding connection remains open throughout check→run→verify after acquisition; losing the connection cancels execution. The schema field only describes the check target and does not change the database-level lock scope; check scripts must validate the schema against the actual connection settings. shared_id is currently rejected.

When migration is needed, the task blocks and reports the maintenance scope if managed consumers are still running or other clients are connected to the database. It does not automatically alter tables online. Explicitly stop consumers before retrying. Observing other clients requires pg_read_all_stats or equivalent visibility; insufficient permissions prevent write migrations. Database client observation is a conservative snapshot and cannot stop clients that ignore the protocol from connecting afterward. The first version does not support online migrations or automatic maintenance recovery transactions. Drift never triggers automatic stamp/drop. Interrupted write tasks are recorded as unknown and require another check before recovery.

The PageSmith adapter checks only the revision chain, name conflicts for tables pending creation, and the presence of ORM tables/columns at the target revision. It does not prove that all types, indexes, triggers, or historical data migrations are correct. Audit those separately before manual reconciliation. `conflicting_tables` retains the complete list; the UI displays a summary and remediation advice.

## Explicit resources and observed services

workspace:

```yaml
version: 2
root: .
discover: false
registrations: [.stackharbor/backend.yaml]
resources:
  database:
    name: PostgreSQL
    adapter: compose
    file: docker-compose.yml
    project: pagesmith
    service: db
    available: healthy
    control: managed
    lifetime: persistent
```

An ordered Compose file set, project_directory, env_files and project define the configuration scope. Physical locks remain keyed by Docker daemon/project/service; duplicate project/service registrations are rejected even when their files differ. All explicitly declared input paths must resolve within the root. healthy requires a Compose healthcheck. control is managed / observe; lifetime is persistent / session. Stopping a single project or all applications does not stop persistent containers, and q preserves persistent / observe resources; stopping or restarting containers is an explicit action that handles managed downstream nodes. In v2, `d` displays only explicitly registered resources; resources from multiple Compose projects are controlled separately by node ID. Health and container IDs are observed continuously; instance changes require dependency checks to run again.

Each resource accepts either file or a non-empty ordered files list, and service_started / service_healthy edges. Compose dependencies must also be explicitly registered in the same configuration scope. Dependencies on one-shot completion, optional/restart extensions, and include/profiles/extends are rejected rather than silently downgraded. StackHarbor does not build images, delete volumes, or implicitly start undeclared dependencies.

Observed services with `control: observe` must not declare run/stop; they require ports, ready, and `identity: {command: [absolute executable, argument prefix]}`. Identity checks verify the listening PID/creation time, cwd, and argv prefix; a failed check cannot satisfy dependencies. Read-only observation grants no permission to stop the process. A replacement process must be verified again. Managed services without a probe display started; v1 dependency semantics remain compatible.

## CLI and records

```sh
stackharbor validate --workspace workspace.yaml --json
stackharbor plan start --target backend/service/api --workspace workspace.yaml
stackharbor doctor --target backend/task/migrate --workspace workspace.yaml
stackharbor task run backend/task/migrate --workspace workspace.yaml
stackharbor history --root /path/to/project
```

plan is read-only and does not execute scripts. It exports configuration summaries, targets, topological layers, edges, and actions; migration status and the actual running set for stop/restart are marked for verification at execution time. It is not a credential that preauthorizes online migration. doctor explicitly executes the read-only check stage; a nonzero check exit is returned as an execution failure. task run is explicit execution and handles the task's resource prerequisites.

Events and task-stage logs are written to the root's `.lock.events.jsonl` in the cache with operation/attempt IDs, mode 0600, rotation at 2 MiB, and one retained previous file. history is read-only and can read the current session; it ignores an incomplete final line and reports other corruption as an error. Common secret/password/token environment values and URL user information are redacted; adapters should still sanitize custom secrets that StackHarbor cannot recognize. Records can be reviewed; they do not automatically restore old PIDs or blindly trust old task results.

Compatibility: a v1 workspace can explicitly import v1/v2 registration files while preserving existing v1 node IDs; a workspace that declares its own resources must use version 2. Pure v1 discover/validate still uses JSON schema 1; workspaces containing v2 registrations output schema 2 node projections. Neither outputs environment values.


## Ordered Compose inputs

```yaml
resources:
  database:
    adapter: compose
    files: [backend/compose.yaml, backend/compose.local.yaml]
    project_directory: backend
    env_files: [backend/.env]
    project: my-local-project
    service: db
    available: healthy
    control: managed
    lifetime: persistent
```

`file` remains supported as a single-file shorthand and cannot coexist with `files`. All input paths are relative to the workspace YAML; symlinks are resolved and checked against the root. `project_directory` defaults to the first Compose file's directory. `env_files` uses Compose's ordered `--env-file` semantics, including Compose interpolation and process-environment precedence; this differs from application `context.env_files`. Omit it to use Compose's default environment-file behavior. No override files are discovered implicitly. Include an optional override only when it exists; missing or duplicate files are errors.

All v2 Compose resources, including single-file ones, use `docker compose config --format json`. Validation requires the Docker CLI and Compose plugin, but configuration parsing itself does not require a running engine. Container observation and actions still require an engine. v1 discovery is unchanged.

Validation, plans, control and observation share the same scope and frozen process environment. Explicit input changes or changes to the resolved model invalidate container operations and require reopening the workspace and making a new plan. This covers default `.env` changes that affect the model. Stop/close refuse changed container configuration; local processes can still be cleaned up, and incomplete resource cleanup is reported. The pre-action check is not an atomic filesystem snapshot: do not edit Compose inputs while actions run.

Resolved configuration may contain credentials. StackHarbor keeps it in memory, publishes only a digest as plan evidence, and suppresses raw CLI output in configuration/action errors. Resolution has a 10-second timeout and bounded output (8 MiB stdout, 64 KiB stderr). For diagnostics, inspect the input files and plugin locally without sharing unredacted configuration.

See [the runnable two-file example](../../../examples/compose-multi-file/stackharbor.workspace.yaml). `stackharbor validate --root examples/compose-multi-file --json` parses and validates only; it does not start the Redis container.
